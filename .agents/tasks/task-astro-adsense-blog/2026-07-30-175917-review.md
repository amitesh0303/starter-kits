# Astro static blog starter with AdSense, consent, and RSS

A complete standalone Astro 5.x blog starter implementing MDX content collections with typed schemas, a responsive reserved-space Ad component, a shared consent store gating both advertising and analytics, Article JSON-LD structured data, RSS feed with eligibility filtering, and comprehensive built-output tests (SEO property tests, Playwright ad dimensions, accessibility, CLS). The approach cleanly separates content schema (Zod validation with title/description length bounds), SEO projection (IndexableDocument + metadata generation), and runtime behavior (consent-gated ad loading and analytics initialization).

Watch for: Consent banner never displays on first visit due to `DEFAULT_STATE.updatedAt` being current time, not epoch (confirmed). Tablet ad dimension test (468x60) is mislabeled and actually asserts desktop dimensions at 768px viewport (confirmed). `initAnalytics` leaks subscriptions on repeated calls (confirmed). `loadConfig()` is defined but never consumed by the Ad component or analytics initializer (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The content layer uses Astro's Content Layer API with glob loaders and Zod schemas enforcing title (30-60 chars) and description (50-160 chars) bounds. Draft/future-dated articles are filtered from the index, RSS, and sitemap at build time while still receiving their own statically-generated detail pages with `noindex` robots directives. The deterministic ordering invariant (date descending, slug ascending as tie-breaker) is duplicated across the index page, category page, RSS endpoint, and the `getRssEligibleArticles` utility.

The consent store is an in-memory singleton backed by localStorage, with a subscriber pattern for reactive updates. A single state object gates advertising and analytics independently, though the consent banner always grants or revokes both together. The banner display logic is broken: `DEFAULT_STATE` sets `updatedAt` to the current ISO timestamp, so on a fresh visit the condition `!consent.updatedAt || consent.updatedAt === new Date(0).toISOString()` is never true and the banner stays hidden.

The Ad component reserves exact CSS dimensions per breakpoint (mobile 320x100, tablet 468x60, desktop 728x90) using explicit width/height and box-sizing: border-box to account for the 1px border. The test suite's "tablet 468x60" test uses a 768px viewport which exceeds the 728px desktop breakpoint, so it actually validates desktop dimensions and the true tablet range (468-727px) has no Playwright coverage.

A typed config module (`loadConfig()`) validates env vars and detects placeholders, but neither the Ad component's client script nor the analytics initializer calls it. The Ad component always renders its placeholder regardless of config; the analytics initializer checks consent state but not whether a valid analytics ID exists. This means the config layer is dead code in the current integration.

The test suite has strong property-test coverage via fast-check for RSS eligibility invariants, schema bounds, and consent state transitions. Built-output tests validate SEO metadata, JSON-LD, internal links, RSS XML, accessibility (axe-core), and CLS. The Playwright tests spin up a custom static HTTP server per suite, each on a different port (4173-4175), which works for sequential runs but could collide in parallel.

1. **Consent banner never shows** — `DEFAULT_STATE.updatedAt` is `new Date().toISOString()` (current time), so the display condition in BaseLayout (`!consent.updatedAt || consent.updatedAt === new Date(0).toISOString()`) is never true on first visit. 3. **Subscription leak in initAnalytics** — Each call to `initAnalytics()` registers a new `subscribeConsent` callback unconditionally. BaseLayout calls it on Accept click and again on page load if consent was already granted. Guard the subscription or move it outside the function.
4. **loadConfig is dead code** — `loadConfig()` in `src/lib/config.ts` is never imported by any page, component, or script. The Ad component doesn't check `isAdsenseEnabled` before loading the provider, and the analytics initializer doesn't check `isAnalyticsEnabled`. Either wire config into the ad/analytics flow or remove it.
5. **Hardcoded port collision risk** — Output test suites use three fixed ports (4173, 4174, 4175) for their embedded HTTP servers. If Vitest runs suites in parallel (the default), tests will fail with EADDRINUSE. Consider using port 0 for random assignment or ensure serial execution.
6. **Sorting logic duplicated four times** — The date-descending + slug-ascending sort appears in `index.astro`, `categories/[slug].astro`, `rss.xml.ts`, and `src/seo/rss.ts`. Extract a shared `sortArticles` utility to prevent future divergence.

## Consent banner display logic defect

The `consent-store.ts` module initializes `DEFAULT_STATE` with `updatedAt: new Date().toISOString()`, producing a non-empty timestamp string representing the current moment. In `BaseLayout.astro`, the banner-display decision is:

```typescript
if (!consent.updatedAt || consent.updatedAt === new Date(0).toISOString()) {
  banner?.removeAttribute('hidden');
}
```

On a fresh visit with no localStorage entry, `getConsent()` returns `DEFAULT_STATE` where `updatedAt` is a real ISO timestamp (e.g., `"2025-01-15T10:00:00.000Z"`). The first condition (`!consent.updatedAt`) is false because a non-empty string is truthy. The second condition compares against epoch (`"1970-01-01T00:00:00.000Z"`), which also fails. The consent banner is effectively dead UI — it never becomes visible, so users cannot grant consent through the intended flow. This means advertising consent stays `false` permanently unless something else calls `setConsent`.

## Tablet viewport test gap

The Ad component CSS defines three breakpoints:
- Default (< 468px): 320x100
- `@media (min-width: 468px)`: 468x60
- `@media (min-width: 728px)`: 728x90

The test named "reserves 468x60 at tablet viewport (768px)" sets viewport width to 768px. At 768px, the `min-width: 728px` rule applies, overriding the tablet rule. The test then asserts `width: 728, height: 90` — which matches desktop, not tablet. The test description claims to verify tablet behavior but its assertions match the dimensions it actually renders (desktop). The true tablet band (468-727px) has zero Playwright coverage. A viewport of 500-700px would exercise the 468x60 breakpoint.

## Analytics subscription leak

```typescript
export function initAnalytics(): void {
  const state = getConsent();
  if (state.analytics && !initialized) {
    activateAnalytics();
  }
  subscribeConsent((newState) => { // registered unconditionally every call
    if (newState.analytics && !initialized) {
      activateAnalytics();
    }
  });
}
```

Every invocation adds a new subscriber to the consent store's `Set<ConsentSubscriber>`. In BaseLayout, `initAnalytics()` is called immediately if `consent.analytics` is true, and again when the Accept button is clicked. On SPA-style navigations or page reloads with prior consent, multiple subscriptions accumulate. Since `activateAnalytics()` guards against double-init via the `initialized` flag, the leaked closures are functionally inert but waste memory and subscriber iteration time.

## Config module disconnected from runtime

`src/lib/config.ts` exports `loadConfig()` which validates env var presence and rejects placeholder values. However, neither `Ad.astro`'s client script nor `analytics/index.ts` calls `loadConfig()`. The Ad component unconditionally renders its placeholder and sets `data-consent-granted` based solely on consent state. The analytics initializer dispatches a `CustomEvent` without checking whether a valid measurement ID exists. In the starter's current state, `loadConfig()` is unreferenced production code — it serves as documentation of the design intent but doesn't enforce the fallback behavior it describes.

## Deterministic ordering duplication

The sort pattern `b.data.publishedAt.getTime() - a.data.publishedAt.getTime()` with slug tie-breaker appears in:
- `src/pages/index.astro` (lines 14-18)
- `src/pages/categories/[slug].astro` (lines 36-40)
- `src/pages/rss.xml.ts` (lines 15-18)
- `src/seo/rss.ts` (lines 19-22)

If the ordering contract changes (e.g., adding a secondary sort on `updatedAt`), four locations must be updated in sync. The `getRssEligibleArticles` function in `src/seo/rss.ts` is the closest to a shared utility but it combines filtering and sorting, and the page-level sorts don't use it.
