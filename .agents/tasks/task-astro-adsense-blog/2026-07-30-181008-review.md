# Astro AdSense blog starter — v2 review

All six issues from the v1 review are resolved: the consent banner now displays correctly (empty `updatedAt` default), the tablet ad test validates the right breakpoint (600px viewport asserting 468x60), the analytics subscription leak is guarded, `loadConfig` is wired into both the Ad component and the analytics initializer, all output test suites use OS-assigned ports (`server.listen(0)`), and sorting logic is extracted into `src/lib/sort-articles.ts` consumed by all four callers.

Watch for: Sitemap exclusion relies on slug substring matching (`/draft-`) rather than the actual `draft` frontmatter field, which will incorrectly exclude non-draft articles whose slugs contain "draft-" and fail to exclude drafts with other slug patterns (confirmed). The Ad component sets both `aria-hidden="true"` and `role="complementary"` with `aria-label`, which is contradictory — the element is hidden from the accessibility tree yet declares a landmark role (confirmed).

**Verdict**: APPROVED

## High-level view

The consent store's default state uses an empty `updatedAt`, making the banner-display check (`if (!consent.updatedAt)`) work as a simple falsy guard. The `subscribed` flag in `initAnalytics` prevents subscription accumulation without introducing cleanup complexity. The `sortArticles` utility is a pure function that all four consumers import directly, eliminating the duplication risk.

The sitemap filter in `astro.config.mjs` uses a URL pattern (`!page.includes('/draft-')`) as a heuristic for draft exclusion. This works for the current sample content where the draft article's slug literally starts with "draft-", but the filter is semantically disconnected from the `draft: boolean` field that governs indexability everywhere else. Since Astro's sitemap integration operates on generated URLs at build time (not on collection entries), there's no straightforward way to reference frontmatter in the filter callback — the README should document that draft article filenames must be prefixed with "draft-" to align with the sitemap filter.

The ARIA conflict on the Ad container won't trigger axe-core failures (the element is hidden, so axe skips it), but it signals unclear intent about whether the ad space should be announced as a landmark or hidden entirely.

## Sitemap filter semantics

In `astro.config.mjs`:

```javascript
sitemap({
  filter: (page) => !page.includes('/draft-'),
}),
```

The actual drafts mechanism throughout the codebase uses `article.data.draft === true` to exclude content from the index, RSS, and robots. The sitemap filter is the only place that falls back to a slug-pattern heuristic. Since `getStaticPaths` in `articles/[slug].astro` generates pages for all articles (including drafts, which receive `noindex` meta), a draft page with a slug like "my-new-post" would end up in the sitemap despite being noindexed, and a published article named "draft-process-explained" would be erroneously excluded.

## ARIA attribute conflict on Ad component

```html
<div
  class:list={['ad-container', className]}
  data-ad-slot={slot}
  aria-hidden="true"
  role="complementary"
  aria-label="Advertisement"
>
```

Setting `aria-hidden="true"` removes the element and all descendants from the accessibility tree. The `role="complementary"` and `aria-label="Advertisement"` have no effect since the element is invisible to assistive technology. Keep `aria-hidden="true"` and drop `role`/`aria-label`, since ad containers are decorative/supplementary and intentionally hidden from screen readers.
