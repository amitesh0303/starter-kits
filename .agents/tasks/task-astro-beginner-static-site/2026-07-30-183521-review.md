# Beginner static Astro starter kit (v2)

Adds a complete `astro-beginner-static-site` starter delivering four static pages with Astro 5.18, plain CSS, shared layout/navigation/footer, two reusable components (Hero, Card), SEO meta tags, sitemap, beginner comments, and a Vitest + Playwright test suite covering accessibility, keyboard focus, viewport overflow, link validation, and a Property 14 dependency allowlist. All four v1 issues have been addressed. Watch for: relative-path link resolution in `links.test.ts` uses `resolve()` with a path fragment, which would misresolve relative `href` values — currently unreachable since all links are absolute, but fragile if content changes (possible).

**Verdict**: APPROVED

## High-level view

The link validation test in `tests/output/links.test.ts` has a relative-path resolution branch that calls `resolve(fileRelDir, normalizedHref)` where `fileRelDir` is a path fragment like `/about/`. On POSIX this accidentally works because the fragment starts with `/` and `path.resolve` treats it as absolute, but the semantics are wrong (filesystem path space vs URL path space). Currently unreachable because all links in this starter are absolute or external, but would break silently if someone adds relative hrefs later.

## Relative link resolution fragility in links.test.ts

The link validation test handles relative `href` values with:

```ts
const fileRelDir = file.replace(distDir, '').replace('/index.html', '/');
normalizedHref = resolve(fileRelDir, normalizedHref).replace(/\/+/g, '/');
```

`fileRelDir` produces a fragment like `/about/`. When passed to `path.resolve()`, it's treated as an absolute path on the filesystem (starts with `/`), and the second argument is resolved relative to it. On macOS/Linux, `resolve('/about/', 'sibling')` yields `/about/sibling` — which accidentally looks correct as a URL path. On Windows the leading `/` isn't treated as a root, so the result would differ. The correct approach would use `join('/', fileRelDir, normalizedHref)` to stay in URL-path space rather than relying on POSIX filesystem semantics.

Since every link in the current pages is either absolute (`/about/`), external (`https://`), or `mailto:`, this branch never executes. It's a latent bug that only manifests if someone adds `<a href="./other">` or similar relative links.
