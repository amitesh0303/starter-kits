# Beginner static Astro starter kit

Adds a complete `astro-beginner-static-site` starter to the multi-stack boilerplate repository. The starter delivers four static pages (Home, About, Contact, Projects) using Astro 5.18 with plain CSS, a shared layout with navigation and footer, two reusable content components (Hero, Card), SEO meta tags, sitemap generation, beginner-oriented comments, and a full Playwright + Vitest test suite covering accessibility, keyboard focus, viewport overflow, link validation, and a Property 14 dependency allowlist. Watch for: the `overflow-x: hidden` CSS rule masks overflow rather than proving its absence (confirmed), the static server in output tests has no path-traversal guard (confirmed), and starter.json `status` is `"pending"` while root README says `"in progress"` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The overflow test checks `scrollWidth <= clientWidth` on the rendered page, but `global.css` sets `overflow-x: hidden` on `<html>`, which clips overflowing content and forces `scrollWidth` to equal `clientWidth` even when child elements exceed the viewport. The test passes by definition rather than detecting a real layout issue.

Status tracking is inconsistent: starter.json retains `"status": "pending"` while the root README was updated to `"in progress"`. If any automation reads starter.json to determine project state, this mismatch could cause confusion.

The output test files (accessibility, overflow, keyboard-focus) each spin up an independent static file server via `createServer`. The request handler resolves paths with `join(dir, req.url)` without sanitizing directory traversal sequences. Three copies of the same ~30-line server utility also create a maintenance burden.

## Overflow test integrity

The global stylesheet applies `overflow-x: hidden` to the root `<html>` element:

```css
html {
  /* Prevent horizontal overflow at all viewports */
  overflow-x: hidden;
}
```

Meanwhile the overflow test asserts:

```ts
const scrollWidth = await page.evaluate(() => document.documentElement.scrollWidth);
const clientWidth = await page.evaluate(() => document.documentElement.clientWidth);
expect(scrollWidth).toBeLessThanOrEqual(clientWidth);
```

When `overflow-x: hidden` is set on the element being measured, the browser clips overflow and reports `scrollWidth === clientWidth` regardless of whether child content actually exceeds the viewport boundary. A genuine overflow regression (e.g., a 500px-wide fixed-width element on a 375px screen) would go undetected.

Two remediation options: remove the `overflow-x: hidden` rule entirely (the responsive CSS already keeps content within bounds), or change the assertion to measure `document.body.scrollWidth` against `window.innerWidth`, which isn't affected by the html element's overflow clipping.

## Static server path handling in tests

Each of the three Playwright-based test files (`accessibility.test.ts`, `overflow.test.ts`, `keyboard-focus.test.ts`) contains an identical `createStaticServer` implementation. The handler uses:

```ts
let filePath = join(dir, req.url ?? '/');
```

No validation prevents `../` traversal. A URL like `/../package.json` would resolve outside `dist/`. The practical risk is low (localhost-only, test-time-only) but the pattern is easily hardened with a single `resolve(dir, '.' + pathname)` and a prefix check.

The three copies are also a maintenance concern. If the server logic needs to change (e.g., to support query-string stripping or 404 pages), three files need updating. A shared `tests/helpers/static-server.ts` module would eliminate this.

## Status field inconsistency

The root README was updated:

```diff
-| ⏳ pending | [`astro-beginner-static-site`](...) |
+| 🚧 in progress | [`astro-beginner-static-site`](...) |
```

But `starter.json` inside the starter directory still declares:

```json
"status": "pending"
```

The catalog validator script reads `catalog/starters.json`, which also says `"pending"`. If the orchestrator's status-promotion logic checks starter.json or the catalog entry, it won't see the "in progress" state reflected in the README.
