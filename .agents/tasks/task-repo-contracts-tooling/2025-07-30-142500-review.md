# Repository contracts and read-only catalog tooling

This change bootstraps the entire root infrastructure for a 52-starter-kit repository: a normative JSON catalog with closed schema, a root README with validator-parseable family sections, a hand-rolled schema validator (no Ajv), 36 property-based tests via fast-check, and two CI workflows (catalog validation on Win+Linux, per-starter isolated testing with fake credentials). The approach is deliberately "contracts first" — no starter code exists yet; only the tooling that will enforce invariants once starters land.

Watch for: the `final-completion` CI job will fail on every main push until all 52 starters reach `complete` status (confirmed); the independence checker produces false positives on `../` inside URLs or string values (confirmed); the starter-ci workflow uses `/tmp/starter-test` as a working directory on Windows runners where Git Bash may or may not resolve this correctly depending on shell (likely).

**Verdict**: APPROVED

## High-level view

The catalog and schema define a closed 52-entry contract with exact family counts (15/9/12/14/2), all entries currently `pending`. The schema is JSON Schema draft-compatible in structure but validated by a custom engine that only enforces the specific constraints the custom code implements (type, enum, min/max, pattern, array item types) — it will silently pass entries that violate constraints it doesn't implement (minLength, minItems, conditional logic).

The starter-ci workflow implements a "detect changed starters then fan out" pattern with fake environment variables covering the credential surface. The `final-completion` gate rejects anything short of all-complete and will block the workflow on every main push until the repository is done — this is premature given no starters exist yet.

The test suite exercises the four design-spec properties (set equality, dependency closure, manifest/lockfile reproducibility, README mapping) via fast-check. Not tested: the regex-based independence checker's edge cases, `validateExpoIdentifiers`, and the `validateFolders` code path with actual starter.json files on disk.

1. **final-completion blocks main immediately** — The `final-completion` job runs `if: always()` on main pushes and calls `--final-completion` which fails when any starter is pending. Either gate it behind a manual trigger / environment variable, or remove it until starters begin shipping.
2. **Independence checker false positives on `../` in non-dependency strings** — The regex `/"[^"]*\.\.\//g` matches any quoted string containing `../`, including URLs in `description`, `homepage`, or comments. Narrow the match to dependency-value positions only.
3. **/tmp path on Windows runners** — `starter-ci.yml` uses `/tmp/starter-test` with `shell: bash`, which works under Git Bash (mapped to a temp dir), but `working-directory` is resolved by the runner, not the shell. If the runner resolves it literally as a POSIX path, the step may fail on Windows. Consider using `${{ runner.temp }}` instead.
4. **No `$schema` reference in catalog schema** — `starters.schema.json` lacks a `$schema` declaration, so tooling like VS Code and standard JSON Schema validators won't auto-detect the dialect. Add `"$schema": "https://json-schema.org/draft/2020-12/schema"`.

## final-completion gate fires prematurely

The `starter-ci.yml` defines a `final-completion` job:

```yaml
final-completion:
  needs: [starter-test]
  if: always() && github.ref == 'refs/heads/main'
```

This runs on every push to `main` regardless of whether `starter-test` was skipped (because `if: always()` overrides the skipped-dependency behavior). It invokes `node scripts/validate-catalog.mjs --final-completion`, which calls `validateFinalCompletion` — a function that emits one diagnostic per non-`complete` entry. With all 52 starters at `pending`, this job always exits 1. The workflow will show a perpetually red check on `main` until the very last starter ships. Either gate it behind a condition (e.g., only when a `final-gate` label is applied), wire it to `workflow_dispatch`, or simply remove it until starters exist.

## Independence checker regex over-matches

`checkIndependenceViolations` applies four regexes to the full manifest string:

```javascript
{ pattern: /["'][^"']*\.\.\//g, label: 'parent-path reference' }
```

This matches any quoted substring containing `../` — not just dependency values. A `"homepage": "https://example.com/docs/../overview"` or a monorepo migration note in `description` triggers a false positive. The other three patterns (`file:`, `link:`, `workspace:`) similarly match anywhere in the file, though those are less likely to appear in non-dependency contexts. The fix is to parse the JSON and walk only the `dependencies`/`devDependencies`/`peerDependencies` values, or at minimum restrict the regex to lines that look like dependency declarations.

## /tmp vs runner.temp on Windows

The starter-ci isolates each starter by copying it to `/tmp/starter-test`. GitHub Actions Windows runners use Git Bash for `shell: bash` steps, where `/tmp` maps to a Windows-local temp directory — so the `run:` steps should work. However, the `working-directory:` key is resolved by the Actions runner process itself (not by bash), and its behavior with POSIX paths on Windows has historically been fragile. Using `${{ runner.temp }}/starter-test` would guarantee portable resolution at the runner level without relying on Git Bash's `/tmp` mapping.

## Custom schema validator will silently under-validate

The hand-rolled `validateSchemaEntry` does not enforce `minItems`/`maxItems` on arrays, `minLength`/`maxLength` on strings, or composed `$ref` logic. If the schema grows conditional constraints or tighter string bounds, the validator will pass entries that a standard JSON Schema validator would reject. Worth documenting this limitation in a code comment so future contributors know to extend the engine when extending the schema.
