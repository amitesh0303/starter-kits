# Next.js Supabase SaaS Starter (v2 review)

The v1 blocking issues (provider wiring, migration ordering, mail adapter selection) have been addressed. The remaining concerns are lower-severity but include a data-integrity issue in the invite flow: the invite action stores the invitee's raw email string as the `user_id` in the memberships table, which is typed as UUID and checked against `auth.uid()` in RLS policies. This will either fail at insert time (Postgres type rejection) or produce a membership row that can never pass RLS. The placeholder detection function also has a gap: `.env.example` ships values like `sk_test_placeholder` that don't match the exact-equality check in `isPlaceholderValue`, so copying `.env.example` without editing will attempt real SDK instantiation with invalid keys. Watch for: invite membership storing raw email as UUID column value (confirmed), placeholder detection missing `.env.example` default values (confirmed), non-atomic tenant+membership creation leaving orphaned tenants on partial failure (likely).

**Verdict**: APPROVED

## High-level view

The invite flow writes the invitee's email into `memberships.user_id` (a UUID column). The insert will be rejected by Postgres because email strings aren't valid UUIDs. Even if the column were text, no acceptance mechanism exists to swap the placeholder for the real `auth.uid()` after signup, so the invited user would never match the RLS policies. The invite feature is non-functional as implemented.

Placeholder detection uses exact string equality against a short static list. The `.env.example` values (`sk_test_placeholder`, `whsec_placeholder`) don't appear in that list, so `isPlaceholderValue` returns `false` for them. The provider system will instantiate real Stripe/Resend SDKs with these invalid keys, failing on first API call rather than falling back to fakes.

Tenant creation and owner-membership creation are separate queries with no transaction boundary. A failure between them leaves an orphaned tenant row invisible to its owner via RLS (the SELECT policy requires a matching membership row).

The webhook route constructs its own `StripeBillingAdapter` rather than using `getProviders().billing`, duplicating SDK instantiation per request. Functionally equivalent since state lives in Postgres, but wasteful.

<summary>Issues (4)</summary>

1. **Invite stores email as user_id, breaking RLS** — `inviteMemberAction` passes the raw email string as `userId` to `membershipRepo.create()`. The `memberships.user_id` column is UUID-typed and compared against `auth.uid()` in every RLS policy. The insert will fail at the database level (type mismatch), and even if it succeeded, no code path exists to swap the email for the real UUID after signup. Add an invite-acceptance route or use a separate `invites` table.
2. **Placeholder detection misses `.env.example` values** — `isPlaceholderValue` checks exact/case-insensitive equality against `["your-value-here", "placeholder", "CHANGE_ME", "xxx", ""]`. The `.env.example` ships `sk_test_placeholder`, `whsec_placeholder`, `re_placeholder`, `price_placeholder` which don't match. If a developer copies `.env.example` without editing, the provider system attempts real SDK instantiation with invalid keys and fails at runtime rather than gracefully using fakes.
3. **Webhook route duplicates billing adapter construction** — The webhook route's `createBillingAdapter()` replicates the same logic as `getProviders().billing` with its own Supabase client and Stripe instance. Use `getProviders().billing` instead.
4. **Tenant+membership creation is not atomic** — `createTenantAction` creates the tenant, then creates the membership in a separate query. If the membership insert fails, the tenant exists without an owner membership, becomes invisible via RLS, and is unrecoverable without service-role intervention.

## Invite membership stores email as UUID

In `app/dashboard/tenants/[tenantId]/members/invite/page.tsx`:

```typescript
await membershipRepo.create({
  tenantId,
  userId: email, // Placeholder until user accepts invite
  role: role as "member" | "admin",
});
```

The schema defines `user_id UUID NOT NULL` in migration 002. Postgres will reject this insert because an email address like `teammate@example.com` is not a valid UUID literal. The `handleSupabaseError` function will catch the Postgres error and surface a generic "Database operation failed" message.

Even if the column type were relaxed to TEXT, the RLS policies all compare `memberships.user_id = auth.uid()`. An email string will never equal a UUID from Supabase Auth, so the invited user (after signup) would still not match the membership row and would be denied access to the tenant.

No route in the application handles invite acceptance or performs the email-to-UUID swap.

## Placeholder detection does not cover .env.example defaults

```typescript
const PLACEHOLDER_VALUES = [
  "your-value-here",
  "placeholder",
  "CHANGE_ME",
  "xxx",
  "",
];

function isPlaceholder(value: string | undefined): boolean {
  if (!value) return true;
  return PLACEHOLDER_VALUES.some(
    (p) => value === p || value.toLowerCase() === p.toLowerCase()
  );
}
```

The `.env.example` file ships:
- `STRIPE_SECRET_KEY=sk_test_placeholder`
- `STRIPE_WEBHOOK_SECRET=whsec_placeholder`
- `RESEND_API_KEY=re_placeholder`
- `STRIPE_PRICE_ID=price_placeholder`

`isPlaceholderValue("sk_test_placeholder")` returns `false` because `"sk_test_placeholder" !== "placeholder"` (exact equality, not substring). The `getProviders()` function will proceed to instantiate `StripeBillingAdapter` with `sk_test_placeholder` as the API key, which will throw a Stripe authentication error on the first API call.

Fix: use a substring check (`value.toLowerCase().includes("placeholder")`) or add the `.env.example` defaults to the list.

## Non-atomic tenant + membership creation

```typescript
// app/dashboard/tenants/new/page.tsx
const tenant = await tenantRepo.create({ name, slug, ownerId: user.id });
await membershipRepo.create({
  tenantId: tenant.id,
  userId: user.id,
  role: "owner",
});
```

Two independent Supabase queries, no transaction wrapper. If the membership insert fails, the tenant row exists with `owner_id = user.id` but no corresponding membership. The RLS SELECT policy on tenants requires `EXISTS (SELECT 1 FROM memberships WHERE memberships.tenant_id = tenants.id AND memberships.user_id = auth.uid())`, so the owner cannot see their own tenant. The UPDATE policy uses `owner_id = auth.uid()` which would match, but without SELECT visibility the tenant is effectively orphaned.

Supabase JS client doesn't expose multi-statement transactions directly. Options: use an RPC function wrapping both inserts, or add a compensating delete if the membership insert fails.
