# Next.js Supabase SaaS starter kit

Adds a complete multi-tenant SaaS boilerplate at `nextjs-supabase-saas/` implementing tenant isolation via Postgres RLS, deny-by-default authorization policies, Stripe subscription lifecycle with webhook verification and idempotent event processing, Resend email (with in-memory fake), and a dashboard flow exercising tenant/project/member/billing CRUD. The approach cleanly separates domain (entities + policies), infrastructure (adapters behind port interfaces), and presentation (Next.js App Router pages with server actions). Watch for: the `getProviders()` singleton always returns `FakeBillingAdapter` even when real Stripe credentials are present (confirmed), the webhook route constructs its own adapter bypassing the provider cache creating divergent billing instances (confirmed), and `canAccessProject` is functionally identical to `canAccessTenant` offering no project-level granularity (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The domain layer defines four entities and four deny-by-default policies gated by membership role. `canAccessProject` duplicates `canAccessTenant` with no additional constraint, so any tenant member can access all projects within that tenant with no project-scoped permission model.

Five sequential SQL migrations establish the schema with RLS policies. The tenant SELECT policy in migration 001 references `public.memberships`, which doesn't exist until migration 002 creates that table, creating a forward-dependency that will fail if migrations are applied individually rather than in a single transaction.

The critical runtime issue is provider wiring: `getProviders()` in `providers.ts` always falls through to returning `FakeBillingAdapter` and `FakeMailAdapter` even when real credentials are present. The webhook route bypasses this by constructing its own `StripeBillingAdapter` directly, so webhook processing works but checkout session creation (via `getProviders().billing`) never reaches Stripe.

Test coverage is thorough for policies, config validation, and webhook authenticity (78 tests). Not tested: the webhook route handler itself, `StripeBillingAdapter` with mocked Stripe, `ResendMailAdapter`, Supabase repositories against a database, or the `getProviders()` wiring logic.

<details>
<summary>Issues (6)</summary>

1. **`getProviders()` always returns fake billing** — The `createBillingProvider()` function's final branch unconditionally returns `FakeBillingAdapter`. Checkout and portal actions using `getProviders().billing` will never reach Stripe in production. Wire the real `StripeBillingAdapter` when credentials and DB config are present.
2. **Migration ordering dependency on `memberships` table** — `001_tenants.sql` RLS SELECT policy references `public.memberships`, which doesn't exist until `002_memberships.sql` runs. If migrations are applied individually (not in a single transaction), migration 001 will fail. Either move the tenant SELECT policy to migration 002 or use `IF EXISTS` / deferred policy creation.
3. **`canAccessProject` provides no project-scoped isolation** — It is functionally identical to `canAccessTenant` (checks tenant membership only). Any tenant member can access all projects. If project-level permissions are intended, the policy needs a project-membership or project-visibility check.
4. **`getProviders()` also always returns fake mail** — `createMailProvider()` falls through to `FakeMailAdapter` even with a real Resend key. The `ResendMailAdapter` is never instantiated via the provider system.
5. **Webhook welcome-email uses `getProviders().mail` which is always fake** — `sendWelcomeEmailOnFirstActivation` in the webhook route calls `getProviders()` for mail, meaning welcome emails are never actually sent in production even with valid Resend credentials.
6. **No `updated_at` trigger in migrations** — Tables declare `updated_at` columns but there's no Postgres trigger to auto-update them; the application manually sets `updated_at` in TypeScript. If any direct SQL update skips the application layer, `updated_at` will drift silently.

## Provider wiring never reaches real adapters

`createBillingProvider()` checks whether Stripe credentials are placeholder values, then checks whether Supabase credentials are placeholder values, and then falls through to an unconditional `return new FakeBillingAdapter()`:

```typescript
// lib/server/providers.ts lines 52-70
if (isPlaceholderValue(stripeKey) || isPlaceholderValue(webhookSecret)) {
  return new FakeBillingAdapter();
}
// ...checks supabase config...
if (isPlaceholderValue(supabaseUrl) || isPlaceholderValue(serviceKey)) {
  return new FakeBillingAdapter();
}
// Real adapter requires runtime setup with DB repositories
// Return fake as fallback here
return new FakeBillingAdapter();  // <-- always reached
```

Every call site using `getProviders().billing` (billing page checkout action, billing portal action) will operate against the in-memory fake and never create a Stripe Checkout session. The same pattern applies to `createMailProvider()`: `ResendMailAdapter` is never instantiated through the provider system.

The fix: when credentials pass the placeholder check, instantiate `StripeBillingAdapter` (with service client and repos) and `ResendMailAdapter` (with the API key).

## Webhook route vs provider cache divergence

The webhook route at `app/api/webhooks/stripe/route.ts` creates its own `StripeBillingAdapter` via a local `createBillingAdapter()` that correctly instantiates the real adapter when credentials are present.

```
Checkout flow:   BillingPage -> createCheckoutAction -> getProviders().billing -> FakeBillingAdapter (broken)
Webhook flow:    POST /api/webhooks/stripe -> createBillingAdapter() -> StripeBillingAdapter (works)
```

The system can receive and process webhooks but can never initiate a real checkout, creating a dead subscription flow.

## Migration ordering and RLS forward-reference

Migration `001_tenants.sql` creates a SELECT policy referencing `public.memberships`:

```sql
USING (
  EXISTS (
    SELECT 1 FROM public.memberships
    WHERE memberships.tenant_id = tenants.id
      AND memberships.user_id = auth.uid()
  )
);
```

The `memberships` table is created in `002_memberships.sql`. Postgres will reject the policy creation if the referenced table doesn't exist. This works if all migrations run in a single transaction (Supabase's default behavior with `supabase db push`), but fails if migrations are applied individually or if migration 001 is re-run in isolation.

## Domain policy duplication

`canAccessProject` has an identical implementation to `canAccessTenant`: both check whether `ctx.userId` appears in the memberships array. The function signature implies project-scoped access control, but the implementation provides only tenant-level gating. A developer using this starter might assume projects have independent access control.

## Invite flow produces dead URL

The invite-member action creates a membership record directly (no pending/accept flow). The `inviteUrl` passed to the email template is constructed but never consumed by any route handler in this diff; clicking it would land on the generic dashboard, not an invite-acceptance endpoint.

## Subscription idempotency and failure mode

If the `handleCheckoutCompleted` handler's Stripe API call fails (to fetch subscription details), the event is NOT recorded in `processed_events`, so it will be retried on the next webhook delivery. This is correct fail-closed behavior: no partial state mutation without recording the event.

## Test coverage gaps

Not tested: the actual webhook route handler (`POST /api/webhooks/stripe`), the `StripeBillingAdapter` with a real or mocked Stripe client, the `ResendMailAdapter`, any Supabase repository against a database, the `getProviders()` wiring logic, the middleware session refresh, or any Next.js page/layout rendering.
