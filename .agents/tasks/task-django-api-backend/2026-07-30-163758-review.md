# Django + DRF API backend starter

A complete reference starter implementing a Django 5.1.7 / DRF REST API with token auth (allauth + authtoken), owner-scoped CRUD, Stripe webhook handling with idempotency, correlation ID middleware, structured JSON logs, OpenAPI documentation, and a multi-stage Dockerfile. The design favors runtime configurability (env-driven rate limits, DB backend, Stripe fake mode) and a stable error shape across all failure paths. Watch for: the correlation ID implementation uses thread-local storage without async-safe guards (confirmed), webhook signature verification in fake mode accepts any payload without validation (confirmed), and the subscription-to-user linkage is decoupled from webhook processing so subscriptions created via webhook are orphaned from users (confirmed).

**Verdict**: APPROVED

## High-level view

The project scaffold is a standard Django project with four apps (core, accounts, resources, billing) wired through a single `config/` settings package. Dependencies are exact-pinned in `pyproject.toml` with a frozen `uv.lock`, and the Dockerfile uses a multi-stage build that installs production-only deps and runs gunicorn. The layout is conventional and immediately navigable.

Authentication is handled through DRF's `TokenAuthentication` with custom register/login/logout views that bypass allauth's HTML flows in favor of JSON endpoints. The allauth dependency provides the account model infrastructure and email-uniqueness enforcement but its REST-less architecture means the auth surface is entirely hand-rolled.

Resource CRUD is a standard ModelViewSet with an owner-scoped queryset filter and per-request rate limiting via `django_ratelimit.core.is_ratelimited`. Rate limiting is applied in `initial()` so it gates all viewset actions uniformly. The rate string is derived from two settings (`RATE_LIMIT_REQUESTS`, `RATE_LIMIT_WINDOW`) and the cache backend defaults to Django's `LocMemCache`—fine for single-process but silently per-process in multi-worker deployments.

Stripe integration uses a fake mode toggle that, when active, skips signature verification entirely and parses raw JSON from the request body. In production mode, `stripe.Webhook.construct_event` validates the HMAC. Webhook events are deduplicated via `ProcessedEvent` and processed within an atomic transaction so a mid-processing crash leaves no partial state.

The error handling layer intercepts all DRF exceptions and re-formats them into a stable `{code, message, correlationId, details?}` envelope. Secrets are redacted from error detail values by matching on field name. Correlation IDs are generated or propagated from `X-Correlation-ID` and attached to both responses and thread-local state.

Tests (62 passing) cover auth flows, CRUD lifecycle, rate limiting, webhook signature gating, idempotency, error shape conformance, state restart persistence, and OpenAPI schema presence. Property-based testing via Hypothesis is listed as a dependency but not exercised in any test file.

<summary>Issues (5)</summary>

1. **Thread-local correlation ID is not async-safe** — `CorrelationIdMiddleware` stores the ID in `threading.local()`. Under ASGI with async views, concurrent requests sharing a thread will clobber each other's correlation ID. Use `contextvars.ContextVar` instead.
2. **Fake-mode webhook skips all validation** — When `STRIPE_FAKE_MODE=true`, `verify_webhook_signature` returns parsed JSON with no schema or structural check. A malformed or malicious payload reaches `_process_subscription_event` unchecked. Add minimal field-presence validation even in fake mode.
3. **Rate limit cache is LocMemCache by default** — `django_ratelimit` uses Django's default cache backend, which is `LocMemCache`. In multi-worker deployments (gunicorn with 3 workers as configured), each worker tracks limits independently, effectively multiplying the allowed rate by the worker count. Document or default to a shared cache (Redis/memcached) for production.
4. **Webhook-created subscriptions are user-orphaned** — `_process_subscription_event` calls `update_or_create` on `Subscription` without setting `user`. The `Subscription.user` field is nullable, so these records exist in the database but are invisible to `subscription_status` (which queries by user). Document the expected pairing mechanism (e.g., linking `stripe_customer_id` to user at checkout time).
5. **Hypothesis dependency unused** — `hypothesis==6.119.3` is listed in dev dependencies and the task spec mentions property-based testing, but no test file imports or uses Hypothesis. Either add property-based tests or remove the dependency to avoid confusion.

## Correlation ID propagation via thread-local

The `CorrelationIdMiddleware` stores the per-request ID in a `threading.local()` instance:

```python
_correlation_id: threading.local = threading.local()
```

This works under WSGI (gunicorn sync workers) because each request occupies its own thread. Under ASGI or with Django's async views, multiple request coroutines can share a single thread and overwrite each other's correlation ID. The rest of the codebase (error handler, views) retrieves the ID via `get_correlation_id()` which reads from the same thread-local. The Dockerfile runs gunicorn in sync mode, so today it's safe, but the starter positions itself as production-ready and switching to uvicorn or async views would silently break correlation. A `contextvars.ContextVar` is the drop-in replacement that works in both sync and async contexts.

## Webhook signature verification in fake mode

`stripe_provider.py` implements a binary toggle: real mode delegates to `stripe.Webhook.construct_event`, fake mode does `json.loads(payload)` and returns the result:

```python
if is_fake_mode():
    event_data: dict[str, Any] = json.loads(payload)
    return event_data
```

The webhook view then reads `event_data.get("id")`, `event_data.get("type")`, and dives into `data.object` without guarding against missing keys. In production with real Stripe events this is safe because the SDK validates the schema. In fake mode during integration testing or development, a malformed POST to `/api/webhooks/stripe/` can produce `KeyError` or silently create `ProcessedEvent` records with empty strings as identifiers. This isn't a production security issue (fake mode should never be on in production) but it weakens the test harness: a test that posts partial JSON will produce confusing ORM errors rather than a clean 400.

## Rate limiting scope and cache backend

Rate limiting is applied per-user via:

```python
is_limited = is_ratelimited(
    request=django_request,
    group="api_resources",
    key="user_or_ip",
    rate=rate,
    increment=True,
)
```

The `key="user_or_ip"` is a built-in django-ratelimit key that identifies authenticated users by PK and anonymous users by IP. The rate limit only applies to the `APIResourceViewSet`; other endpoints (auth, webhooks, health, schema) have no rate protection. This is likely intentional (webhooks are already gated by signature, auth endpoints are public) but the Stripe webhook endpoint is a common DDoS target and verifying signatures is not free—consider at minimum a burst limiter on the webhook path.

The Django settings don't define a `CACHES` entry, so Django defaults to `LocMemCache`. The Dockerfile's gunicorn config starts 3 workers, each with its own isolated cache. A user making 100 requests will only hit the limit if all requests land on the same worker.

## Subscription lifecycle and user linkage gap

The `Subscription` model has `user = models.OneToOneField(..., null=True, blank=True)`. The webhook handler creates subscriptions via `update_or_create` keyed on `stripe_subscription_id` but never sets `user`. The `subscription_status` view queries `Subscription.objects.get(user=user)`, so a webhook-created subscription is never visible to any user.

The intended flow is presumably: the application creates a Checkout Session with a user reference, and a separate mechanism (checkout.session.completed event or a direct API call) links the subscription to the user after creation. This mechanism doesn't exist in the starter. For a reference starter this is acceptable—documenting "you must implement checkout flow to link subscription to user" would clarify the gap.

## Test coverage shape

The 62 tests cover:
- Auth: register, login, logout, 401/403 enforcement
- CRUD: full lifecycle, ownership isolation, validation errors
- Rate limiting: threshold enforcement via mock, configurable bound
- Webhooks: valid/invalid signature, state transition, idempotency
- Errors: shape conformance across all error types, no secret leakage
- State restart: connection cycling to prove committed reads survive
- OpenAPI: schema generation, endpoint and auth requirement presence
- Health: 200 response shape

Not tested: concurrent request behavior under rate limiting, webhook processing under database failure (transaction rollback path), allauth account confirmation flow, CORS header presence, gunicorn process lifecycle, and the `subscription_status` endpoint in a successful case (only the 404 path is tested since webhooks never link user). The Hypothesis dependency is imported nowhere—the property-based tests promised by the task spec are absent.
