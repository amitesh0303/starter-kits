# Expo subscription app starter kit

A new Expo React Native starter drops into the multi-stack boilerplates monorepo. It wires up Supabase Auth, RevenueCat purchases, Sentry error reporting, an offline SQLite cache, and a bounded persistent queue behind adapter interfaces with fake defaults so the project runs locally with zero credentials. Property-based tests (fast-check) cover queue capacity/idempotency and monetization routing. The approach is sound: pure domain logic separated from adapters, all external calls gated by a config validator that flips to fake mode on missing credentials.

Watch for: no actual auth guard on the `(app)` route group (confirmed) — navigation relies on redirect from `index.tsx` but a user can deep-link directly into `/(app)/*` unauthenticated; the `purchase.tsx` screen instantiates a module-level `createFakePurchaseAdapter` that leaks between renders and tests (confirmed); the `captureMessage` implementation in the Sentry adapter calls `Sentry.captureException` rather than `Sentry.captureMessage` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The domain layer (`src/domain/`) is pure functions: eligibility routing that enforces digital-only-via-RevenueCat (Property 10), an entitlement reconciliation policy that marks expired subscriptions inactive, and a queue state machine with a six-state lifecycle. The queue policy feeds the `BoundedQueue` in `src/sync/queue.ts`, an in-memory implementation that enforces capacity and idempotency but has no write-through to the SQLite tables that exist for it.

Adapters follow a consistent pattern: a typed interface, a real implementation, and a `createFake*` factory. Configuration flows through `validateConfig()` which reads `EXPO_PUBLIC_*` env vars, rejects placeholder strings, and toggles `isFakeMode` when any required credential is absent. The Sentry adapter applies PII redaction before all captures, but its `captureMessage` path incorrectly calls `Sentry.captureException`, collapsing all messages into a single Sentry issue.

The route structure uses expo-router groups: `(auth)` for sign-in, `(app)` for authenticated screens. A `deep-link.tsx` route handles `exposubscription://` URIs by waiting for hydration then replacing to the target screen. The `(app)/_layout.tsx` declares "auth guard" in a comment but has no actual guard — any deep link bypasses authentication.

Test coverage is broad: 13 suites, 86 tests, property tests with 150 generated cases per property. Route tests are structural (module-loads) rather than behavioral; no test exercises the auth-guard-or-redirect flow.

## Missing auth guard on the (app) route group

`app/(app)/_layout.tsx` exports a plain `<Stack>` with no session check. The comment says "In production, this would check auth state" but the starter ships without one. Since `deep-link.tsx` calls `router.replace("/(app)/premium")` after a 50ms hydration wait, any cold-start deep link navigates into the authenticated group without verifying a token exists in SecureStore. The root `index.tsx` redirects to sign-in, but that only fires when the user navigates to `/` — it's not a gate.

The starter's README documents deep-link testing via ADB intents, meaning a real user following those instructions will bypass auth. The fix is a session check in `(app)/_layout.tsx` that redirects to sign-in when no session is available.

## Sentry adapter: captureMessage semantics

```typescript
// error-reporter.ts, createSentryErrorReporter().captureMessage
captureMessage(message: string, context?: ErrorContext): void {
  ...
  Sentry.captureException(new Error(message), { extra: safeContext });
  ...
}
```

This conflates messages with exceptions in Sentry's issue grouping. A message (e.g., "User attempted purchase while offline") becomes an Error stack trace rooted at the reporter call site. Sentry groups exceptions by stack frame, so all messages reported from this adapter collapse into a single issue. The fix is `Sentry.captureMessage(message, { extra: safeContext })`.

## Module-level state leak in purchase.tsx

```typescript
// app/(app)/purchase.tsx - top level
const purchaseAdapter = createFakePurchaseAdapter("fake-user-001");
```

The fake adapter accumulates `entitlements` in a closure array. Because it's module-scoped, state persists across React Fast Refresh cycles during development and across test imports. Each call to `purchase()` appends to the same array. In tests, this creates ordering dependencies between test suites that import the purchase screen.

## SQLite synchronous calls with no recovery path

`sqlite-repository.ts` uses `db.execSync`, `db.getAllSync`, and `db.runSync` exclusively. These throw synchronously on any SQLite error — corrupt DB file, schema version mismatch, or disk-full conditions. The `createSQLiteRepository` function is called during app startup, and there's no try/catch around `initialize()` at the call site. A corrupt DB on a user's device crashes the app in a loop with no way to recover short of reinstalling.

The mitigation: wrap `initialize()` and cache reads in try/catch, and either delete-and-recreate the DB or fall back to in-memory operation on corruption.

## Queue-to-SQLite persistence gap

The `BoundedQueue` in `src/sync/queue.ts` is in-memory only. The README claims "bounded persistent queue" and the SQLite repository has full queue tables (`pending_actions`), but nothing connects them. The `createBoundedQueue` function accepts `initialActions` but no write-through callback exists. On app restart, queued actions that weren't persisted to SQLite are lost.

The comment in `queue.ts` says "In production, this would be backed by SQLite" — either wire up the persistence or amend the README to say "persistence-ready" rather than "persistent."

## Orphaned syncing actions on crash recovery

The queue state machine defines `syncing` as non-terminal, but the only valid transitions out of `syncing` are `applied`, `conflict`, and `failed` — all of which require the sync handler to complete. If the app is killed mid-sync, on restart the action is loaded (via `initialActions`) in `syncing` state with no path back to `pending`. The `SyncEngine.processQueue()` skips non-pending actions, so the orphaned item is stuck forever.

Adding a `syncing -> pending` transition (or a startup sweep that resets stale `syncing` items) would close this gap.
