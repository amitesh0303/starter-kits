# Expo subscription app starter kit (v2)

The seven issues from v1 have been addressed in commit 3da1a29. One new behavioral issue surfaces now that the auth guard exists: each screen instantiates its own `createFakeTokenStore()`, producing isolated `Map` instances that cannot share auth state. In fake mode, sign-in writes to store A while the auth guard reads from store B — the user can never reach the `(app)` group. The queue persistence interface was added but never concretely wired to SQLite, and the crash recovery path has no test coverage.

Watch for: isolated fake token stores across screens make the auth guard a permanent redirect loop in fake mode (confirmed); queue-to-SQLite persistence wiring is interface-only with no concrete implementation (confirmed); no test exercises crash recovery or persistence write-through (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The three files that touch authentication — `sign-in.tsx`, `(app)/_layout.tsx`, and `deep-link.tsx` — each call `createFakeTokenStore()` at module scope, creating independent in-memory `Map` instances. A token set during sign-in is invisible to the auth guard and deep-link handler. The guard always reads `null` and loops back to sign-in. In "real mode" with the device-backed `secureTokenStore` singleton this wouldn't manifest, but the starter is designed to run in fake mode with zero credentials.

The `QueuePersistence` interface defines `onEnqueue` and `onTransition` callbacks, and the `BoundedQueue` invokes them at the right points. No concrete implementation bridges `QueuePersistence` to `SQLiteRepository` — the README documents write-through but at runtime the persistence parameter is never supplied and the queue remains in-memory only.

The crash recovery path (`recoverOrphanedSyncing`) is structurally correct — the sync engine calls it on creation and any `syncing` action transitions back to `pending` — but no test exercises the recovery method, the `syncing -> pending` policy transition, or the persistence callbacks.

## Isolated token stores break the fake-mode auth loop

Each of the three files that touch authentication creates a fresh `createFakeTokenStore()`:

```typescript
// app/(auth)/sign-in.tsx
const tokenStore = createFakeTokenStore();       // Map instance A
const authAdapter = createFakeAuthAdapter(tokenStore);

// app/(app)/_layout.tsx
const tokenStore = createFakeTokenStore();       // Map instance B

// app/deep-link.tsx
const tokenStore = createFakeTokenStore();       // Map instance C
```

`createFakeTokenStore` returns an object backed by `new Map<string, string>()`. When sign-in calls `authAdapter.signIn()`, it writes a token into Map A. The `(app)/_layout.tsx` auth guard reads from Map B, which is always empty, so `getSessionToken()` returns `null` and the guard redirects back to sign-in.

The fix is to export a single shared fake token store instance from `secure-store.ts` (or an `index.ts` barrel) and import it in all three files, or import the `secureTokenStore` singleton everywhere and let the `expo-secure-store` mock handle the test path.

## Queue-to-SQLite persistence gap (partially resolved)

The v1 review flagged that the queue was in-memory only. The fix added:

- A `QueuePersistence` interface with `onEnqueue` and `onTransition` methods
- Try/catch-wrapped calls to the persistence layer inside `enqueue()`, `transition()`, and `recoverOrphanedSyncing()`
- Constructor support via the options object (`persistence?: QueuePersistence | null`)

What's still missing is the concrete wiring. The `SQLiteRepository` interface has exactly the right methods (`insertAction`, `updateActionState`), but no file creates the adapter that maps between the two interfaces. The README states "Queue state is written through to SQLite via the QueuePersistence interface" — this is aspirationally true but not exercised at runtime. The queue drops all actions on process death.

## Missing test coverage for recovery and persistence

The crash-recovery mechanism added to fix v1 issue #7 has no direct test coverage:

- No queue test creates a queue with pre-existing `syncing` items and asserts they transition to `pending`
- No test verifies that `recoverOrphanedSyncing` fires the persistence `onTransition` callback for each recovered item
- No sync engine test verifies `recoveredOnStartup` is populated correctly
- The `__testTokenStore` export on `_layout.tsx` exists for testing the auth guard but is unused in any test file
